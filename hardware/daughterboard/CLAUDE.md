# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

KiCad project `daughterboard` (formerly codenamed `OuttaControl`/`OuttaQontrol`) — the
8-channel analog board: **DAC80508Z** (8-ch DAC) + **AD7193** (8-ch 24-bit ΔΣ ADC) +
8× **XTR200** current-source front ends + **REF5030** voltage reference + **AT21CS01**
single-wire EEPROM (board ID/config storage, new in this revision) + a **74HC165**
shift register + a `Custom_PCIe_x4` edge connector to the motherboard. 4-copper-layer
board: `F.Cu` / `In1.Cu` / `In2.Cu` / `B.Cu`.

The directory holds **two board revisions**:

- **Top level** (`daughterboard.kicad_pro` / `.kicad_sch` / `.kicad_pcb`) — the current
  revision: adds the AT21CS01 EEPROM and layout improvements over v1.
- **`version 1/`** — the prior revision, kept intact for reference (its own
  schematic/PCB/renders/PDN results). **Don't edit into it** — treat it as an archive.

Everything below (netlists, PCB, PDN/padne workflow) describes the **top-level** (current)
revision; the same file kinds exist under `version 1/` for the old one.

## Sense-input buffer stage (U13–U16, added 2026-08)

Between each 6:1 sense divider and the AD7193 input sits a **unity-gain OPA2333 follower** —
four dual packages, **U13–U16**, eight followers for eight channels. Per channel:

```
heater -> CHx -> 100k -> CHx_B -> OPA2333 follower -> 1k -> CHx_V -> AD7193 AIN
                           |                                  |
                          20k                               100nF
                           |                                  |
                          GND                                GND
```

| pkg | ch A / ch B | A in/out | B in/out | series R | ADC pins |
| --- | --- | --- | --- | --- | --- |
| U13 | CH0 / CH1 | 3 / 1 | 5 / 7 | R28, R29 | U11.11, U11.12 |
| U14 | CH2 / CH3 | 3 / 1 | 5 / 7 | R30, R31 | U11.13, U11.14 |
| U15 | CH4 / CH5 | 3 / 1 | 5 / 7 | R32, R33 | U11.15, U11.16 |
| U16 | CH6 / CH7 | 3 / 1 | 5 / 7 | R34, R35 | U11.17, U11.18 |

Supply pin 8 = +3.3 V, pin 4 = V− = GND. **Use pin 4, not pin 9** — pin 9 is the DRB thermal
pad. `R28`–`R35` (1 k) + `C26`–`C33` (100 nF) form the anti-alias RC into each ADC input.

**Why they exist.** The board previously drove the AD7193 inputs straight from the divider
taps with the ADC's *internal* buffer enabled, which produced a systematic **~3 mV readback
offset** — the open issue from the 8-board test. In buffered mode the AD7193 inputs want
~250 mV of headroom from either rail, and a low-current channel's divider tap sits within
tens of mV of AGND, below that range. Disabling the internal buffer (`CONF.BUF = 0`) fixes
the range problem but leaves the ADC's switched-capacitor input loading the divider's
~16.7 kΩ source impedance, converting the offset into a gain error. The external followers
resolve both: OPA2333 is zero-drift with 10 µV max offset and an input range including
ground, and it presents a near-zero source impedance to the switched-cap input.

This is the textbook trade-off for a ΣΔ front end, and ADI document both horns of it: the
internal buffer "allows source impedances on the front end without contributing gain errors"
but costs 250 mV of range at each rail, while unbuffered operation is rail-to-rail but presents
the sampling capacitor as a dynamic load, so "resistor/capacitor combinations on the input pins
can cause gain errors depending on the source output impedance." With a 16.7 kΩ source we need
the range *and* a low driving impedance, which is precisely what an external follower buys.

- [AN-608, *Input Buffers on Sigma-Delta ADCs*](https://www.analog.com/media/en/technical-documentation/application-notes/an-608.pdf)
- [AD719x Instrumentation Converters FAQ](https://www.analog.com/media/en/technical-documentation/frequently-asked-questions/AD719x_FAQ_Instru_Conv.pdf)
- [EngineerZone: AD7193 AINx Current Issue](https://ez.analog.com/data_converters/precision_adcs/f/q-a/23869/ad7193-ainx-current-issue) — the 250 mV headroom rule, from ADI staff
- [EngineerZone: AD7193 FAQ](https://ez.analog.com/data_converters/precision_adcs/w/documents/16496/ad7193-faq)
- [AD7193 datasheet](https://www.analog.com/media/en/technical-documentation/data-sheets/AD7193.pdf) — RC limits table for unbuffered operation

**This is a hardware+firmware pair.** Boards with U13–U16 fitted *must* run with the AD7193's
`CONF.BUF` cleared; boards without them must not. See the corresponding gotcha in
`firmware/motherboard-test/CLAUDE.md`.

These parts post-date `netlist_v2.net` — regenerate a netlist rather than trusting that file.
Their effect on the PDN model is covered in the padne directives below (quiescent current is
modelled at 34 µA/package; `R28`–`R35` deliberately are not).

## PDN (padne) power-delivery-network simulation

The board's copper planes are simulated for IR drop / current density with an external
tool called **padne**, which solves a resistive-mesh model of the copper pours and
exports per-layer results as VTK unstructured grids for ParaView. This repo only holds
the *inputs/outputs* of that tool, not the tool itself.

- **`pdn*.padne`** (e.g. `pdn_v3.padne` here, `pdn.padne`/`pdn_v2.padne`/`pdn_fine.padne`
  under `version 1/`) — padne's own native project file: a pickled Python blob containing
  `padne.problem.Problem`, `padne.solver.Solution`, and per-layer `shapely` geometry. These
  are **100s of MB and gitignored** (`hardware/daughterboard/**/pdn*.padne` in the root
  `.gitignore`) — never `git add` them; GitHub's 100 MB file limit will reject the push
  (this happened once already — see git history around 2026-07-27).
- **`padne_out_v3/`** — the ParaView export for the current revision: one `.vtu`
  (`UnstructuredGrid`, ASCII `Float64` "voltage" `PointData`) per copper layer —
  `F.Cu.vtu`, `In1.Cu.vtu`, `In2.Cu.vtu`, `B.Cu.vtu` — plus `Archive.zip` (the same
  four files zipped, what you'd hand to `padne_plots_v2.py` directly). Each `.vtu`
  contains one `<Piece>` per electrically-connected copper island on that layer.
  `version 1/` has the analogous `padne_out/`, `padne_out (1)/`, `padne_out_fine/`,
  `padne_out_v2/` for its own solves. `paraview/padne_out/` (+ `.zip`) is a duplicate
  set kept for manually opening in the ParaView GUI.
- **`padne_plots_v2.py`** (top level) / **`padne_plots.py`** (`version 1/`) — turns a
  `padne_out*` export into the two plots actually checked into git:
  `results*/current_density_black.png` (sheet current density, A/m, log scale, black
  background) and `results*/ir_drop.png` (per-net voltage deviation from net median, µV).

  ```bash
  python3 padne_plots_v2.py padne_out_v3/Archive.zip results_v3/   # or a padne_out_v3/ dir directly
  ```

  Requires `numpy` + `matplotlib`. Assumes copper conductivity `SIGMA = 5.8e7 S/m` and
  `THICKNESS = 35e-6 m` for **every** layer — edit those constants at the top of the
  script if the stackup uses thinner inner layers (e.g. 17.5 µm).

  **v2 vs v1 script differences** (why v2 exists, don't revert to v1's logic): v1 dropped
  a piece if `|V|` exceeded a fixed `FLOAT_THRESHOLD`, which silently mis-classified valid
  solves when the whole board floated at an arbitrary offset (happens whenever no
  `VOLTAGE` directive lands on connected copper — harmless since every plot here is
  relative). v2 instead (a) subtracts a `global_offset()` — the median of the largest
  connected piece — before clustering into nets, (b) skips a piece only if it's
  non-finite or its *internal* spread exceeds `MAX_PLAUSIBLE_DROP = 1.0 V` (real
  unconnected-island solver garbage vs. a floating-but-otherwise-fine solve), and
  (c) hard-fails with a pointer to check the padne solve log for "Matrix is exactly
  singular" if literally every piece across every layer came back non-finite, instead of
  silently emitting empty plots. If a re-solve produces garbage-looking plots, that
  singular-matrix case (missing/misplaced source or sink directive in the `.padne`
  project) is the first thing to check.

- `results_v3/` (current rev) — the current output pair described above.
  `version 1/results/`, `results_v2/`, `results-old/` are the prior revision's runs at
  different mesh refinements (`padne_out_fine` = finer mesh solve → `pdn_fine.padne`).
